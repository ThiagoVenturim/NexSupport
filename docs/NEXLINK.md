# NexLink: the Support Engine and the other projects

NexLink is the common message contract of the portfolio (Nextor, NexHub, NexCoder,
nexdash and the Support Engine): one envelope for a project to ask another one for
something and get an answer, instead of each pair inventing its own. This page covers
the Support Engine side:

- the actions it exposes (ingest, suggest a reply, metrics) and the scope each one needs;
- how it consumes the nexdash (askdash) report engine for dashboards;
- tokens, scopes and what never goes into logs;
- the offline examples in `examples/nexlink/`.

The code lives in `support_engine.nexlink`.

## Envelope

```json
{
  "protocol": "nexlink/1",
  "id": "5f0c...",
  "correlation_id": "run-42",
  "kind": "request",
  "sender": "nexhub",
  "target": "nexsupport",
  "action": "support.ingest",
  "params": {"tickets": [{"id": "T-1", "source": "json", "subject": "...", "created_at": "2026-05-04T09:00:00Z"}]},
  "context": {"floor": "support-demo"},
  "sent_at": "2026-05-04T09:00:00Z"
}
```

| Field | Rules |
| --- | --- |
| `protocol` | `nexlink/1`. |
| `id` | Id of this message (generated by default). |
| `correlation_id` | Shared by every message of one conversation, so a chain NexHub -> Support Engine -> nexdash can be followed. A first request without it starts a conversation with its own `id`. |
| `kind` | `request` (ask, wait for the result) or `notice` (tell; the reply only confirms it was accepted and has no result). |
| `sender`, `target` | Project names: lowercase, 2 to 32 characters (`nexhub`, `nexcoder`, `nexdash`, `nextor`, `nexsupport`). |
| `action` | `<namespace>.<name>`, listed in the manifest of the target. |
| `params` | Validated against the action schema; unknown fields are refused. |
| `context` | Small references shared between projects (run id, floor, ticket id): at most 20 keys, values of at most 200 characters. Never ticket text. |

Unknown envelope fields are refused. The token is not part of the JSON body: over
HTTP it travels in `Authorization: Bearer <token>` (or `X-API-Key`); in process it is
passed next to the envelope. The envelope model has a `token` field for in-process
use, and that field is excluded from every dump and hidden from `repr`.

### Reply

```json
{
  "protocol": "nexlink/1",
  "id": "9a1e...",
  "in_reply_to": "5f0c...",
  "correlation_id": "run-42",
  "sender": "nexsupport",
  "target": "nexhub",
  "action": "support.ingest",
  "status": "ok",
  "result": {"ingested": 1, "stats": {"tickets": 1, "chunks": 3, "pii_masked": {"EMAIL": 1}}, "known_tickets": 1},
  "error": null
}
```

On failure `status` is `error` and `error` holds `code`, a generic `message` and, for
validation errors, `details` with field locations and error types only, never the
rejected values.

| Code | HTTP | When |
| --- | --- | --- |
| `invalid_envelope` | 400 | The message is not a valid envelope (or is not JSON) |
| `wrong_target` | 400 | `target` is not this project |
| `invalid_params` | 400 | Parameters do not match the action schema |
| `unauthorized` | 401 | Missing token, or not the token of `sender` |
| `forbidden` | 403 | The token lacks the scope of the action |
| `unknown_action` | 404 | The action is not in the manifest |
| `failed` | 500 | The action raised; the cause is logged by exception type only |
| `upstream_error` | 502 | nexdash refused or failed the report |
| `unavailable` | 503 | A dependency (copilot, nexdash) is not configured or not reachable |

## Actions of the Support Engine

The project name is `nexsupport`. `nexlink.manifest` returns this table with the JSON
schema of each action; NexHub collects the manifests of every project.

| Action | Scope | Parameters | Result |
| --- | --- | --- | --- |
| `nexlink.manifest` | none (any valid token) | none | Project, version and actions |
| `support.ingest` | `ingest:run` | `tickets`: 1 to 500 tickets in the common `Ticket` format | Counters only: tickets, comments kept, chunks, PII masked per kind |
| `support.suggest_reply` | `copilot:suggest` | Same as `POST /v1/suggest` (`ticket`, `namespace`, `now`) | Suggested reply, citations, summary, next step and tone |
| `support.metrics` | `metrics:read` | `dashboard` (default false), `output`, `start`, `end`, `team`, `locale` | Ticket counts by status and answer quality metrics; with `dashboard=true` also `report`, the nexdash `support_metrics` answer |

- `support.ingest` cleans, masks, deduplicates and chunks the tickets with the ingestion
  pipeline, keeps the masked tickets and passes them to an optional sink (for example
  `TicketStore.save_tickets`). The reply never carries ticket text.
- `support.suggest_reply` is listed only when the server is built with a copilot.
- `support.metrics` returns numbers only. Its `report` is the nexdash answer, whose
  dashboard is a self-contained HTML page without scripts.

## Consuming the nexdash report engine

`NexDashClient` builds the request of the nexdash report engine (see the nexdash
`docs/REPORT_ENGINE.md`), validates it locally (unknown fields, model name, period
order, field lengths) and sends it over a transport:

- `RestReportTransport(url)`: `POST /api/reports/run` with `Authorization: Bearer
  <token>`; the token comes from `NEXDASH_ENGINE_TOKEN` (environment or `.env`).
- `EngineReportTransport(engine)`: an in-process `nexdash.engine.ReportEngine`.
  `EngineReportTransport.demo()` runs it on in-memory SQLite with the nexdash synthetic
  data, with no network.

```python
from support_engine.nexlink import NexDashClient

nexdash = NexDashClient.from_env("http://127.0.0.1:8000")
report = nexdash.support_dashboard(start="2026-04-01", end="2026-06-30", team="tier1", locale="pt-BR")
report["data"]["panels"]["csat"]["value"]
report["dashboard"]["html"]  # serve it with the CSP in report["dashboard"]["csp"]
```

On the nexdash server the Support Engine gets its own client token and scopes:

```bash
NEXDASH_CLIENT_NEXSUPPORT_TOKEN=<generated>
NEXDASH_CLIENT_NEXSUPPORT_SCOPES=reports:list,reports:run
```

## Running the server

```python
from support_engine.copilot import CopilotService
from support_engine.nexlink import ClientRegistry, NexDashClient, SupportWorkspace, build_support_server
from support_engine.nexlink.api import create_nexlink_app

server = build_support_server(
    ClientRegistry.from_env(),                    # SUPPORT_ENGINE_NEXLINK_CLIENT_<NAME>_TOKEN / _SCOPES
    workspace=SupportWorkspace(sink=store.save_tickets),
    copilot_service=CopilotService(copilot),      # optional: enables support.suggest_reply
    nexdash=NexDashClient.from_env("http://127.0.0.1:8000"),
)
app = create_nexlink_app(server)                  # POST /nexlink, needs the api extra
```

Calling another project:

```python
from support_engine.nexlink import HttpTransport, NexLinkClient

client = NexLinkClient("nexsupport", HttpTransport("http://127.0.0.1:8100"))
reply = client.request("nexhub", "hub.send_message", {"agent": "builder", "text": "..."})
```

The token for each target comes from `SUPPORT_ENGINE_NEXLINK_TOKEN_<TARGET>`. The
action above is only an illustration; the real names come from the manifest of the
target.

## Security

- Every calling project has its own token and scope list, read only from the
  environment or `.env`:

  ```bash
  SUPPORT_ENGINE_NEXLINK_CLIENT_NEXHUB_TOKEN=<generated>
  SUPPORT_ENGINE_NEXLINK_CLIENT_NEXHUB_SCOPES=ingest:run,metrics:read
  SUPPORT_ENGINE_NEXLINK_CLIENT_NEXCODER_TOKEN=<generated>
  SUPPORT_ENGINE_NEXLINK_CLIENT_NEXCODER_SCOPES=metrics:read
  ```

  Generate tokens with `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
  Tokens shorter than 16 characters, unknown scopes and two clients sharing one token
  are refused at startup. A client without a scopes variable can only read the manifest.
- Each call is checked twice: the token must be the one of the `sender` it claims
  (constant-time comparison), and the client must hold the scope of the action.
- Tokens never appear in logs, replies, error messages or `repr`. The HTTP transport
  sends them in the header only.
- Logs carry the sender, the action, the outcome and the correlation id. They never
  carry parameters, results or ticket text. Failures are logged by exception type.
- Tickets are masked by the ingestion pipeline before they are kept, and the answers of
  `support.ingest` and `support.metrics` are numbers.
- HTTP bodies above 5 MB (configurable) are refused before parsing. Run the HTTP
  endpoint on localhost or a private network; from outside, only through a VPN.

## Examples

`examples/nexlink/` runs offline, with tokens generated in process and synthetic
tickets:

```bash
python examples/nexlink/support_asks_dashboard.py --out dashboards/  # Support Engine -> nexdash
python examples/nexlink/nexhub_triggers_ingest.py                    # NexHub -> Support Engine
python examples/nexlink/nexcoder_reads_metrics.py                    # NexCoder -> Support Engine -> nexdash
```

When `nexdash` is installed they use its real report engine in process; otherwise, or
with `--stub`, a stub with the same answer format. `tests/test_nexlink_examples.py`
runs them in the test suite.
